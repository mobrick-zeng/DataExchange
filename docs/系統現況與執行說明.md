## 版本重點（v0.2_TLS_Demo 相對前版）

- **資料模型全面改版為 v2**：不存債務人個資，案件以「法院代碼＋公文文號」辨識；帳號採**啟用碼**機制；銀行／法院改為完整參考主檔＋`isActive` 後台啟用；還款依 `planRatio` **自動攤提**、尾差由主辦吸收；稽核合併為單一 append-only `AuditLog`。

## 一、一句話總覽

跨銀行「前置調解債權申報／還款管理」平台，前後端整合的**全棧系統**：

> 最大債權行（主辦）建立案件（選法院＋填公文文號）並**代填**各債權行債權明細 → 設定還款計畫與各行 `planRatio` → 邀請其他債權行 → **發布** → 其他債權行**確認／回報異議** → 全數確認後進入**還款中**、主辦逐月輸入實收總額（系統自動攤提到各行） → **結清**或**毀諾終止**。

帳號採**管理員建立＋啟用碼啟用制**，資料存於 **PostgreSQL**，權限一律由**後端強制（Server-side RBAC）**；前端無任何本地資料層，全部呼叫後端 REST API。

## 二、技術架構

| 層 | 技術 | 位置 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite 5 + Tailwind 3 + React Router 6 + Zustand | `src/` |
| 前端資料存取 | 統一經 `src/services/api.ts`（`apiFetch`，自動附 JWT） | `src/services/` |
| 後端 | Fastify 4 + Prisma 5 + Zod（`@fastify/jwt`、bcryptjs、`@fastify/rate-limit`、`@fastify/cors`） | `backend/src/` |
| 資料庫 | PostgreSQL 16 | Docker |
| 部署 | 本機開發（Vite + tsx）或全棧 Docker（db + api + web + Caddy 反向代理／自動 HTTPS） | `docker-compose.fullstack.yml` |

### 認證與帳號模型（啟用碼制）
- **登入**：銀行代碼 + Email + 密碼三層驗證 → 回傳 JWT（效期 **8 小時**，payload 含 `userId / role / bankCode / name`）。失敗訊息一律通用，避免帳號列舉。
- **帳號啟用**：管理員建立帳號（狀態 `PENDING_ACTIVATION`、無密碼）並產生一次性**啟用碼**（雜湊儲存、效期 **3 天**，由外部管道遞送，免 SMTP）。使用者於登入頁「選銀行＋Email＋啟用碼當密碼」→ 後端回 `activationRequired` → 前端切換為**啟用模式**：設定新密碼（≥8 碼）＋**勾選個資使用同意** → 帳號轉 `ACTIVE`（記 `activatedAt`／`consentedAt`／`consentVersion`）並自動登入。
- **登入鎖定**：帳號＋銀行正確、僅密碼錯時累計，連續 **5 次** → 鎖定 **15 分鐘**；管理員可手動解鎖。
- **密碼重設**：使用者於「忘記密碼」送出申請（一律通用回應）→ 管理員核發一次性重置碼 → 使用者以重置碼設定新密碼。管理員亦可主動替帳號核發重置碼。

### 案件狀態機
```
DRAFT → PENDING_CONFIRMATION → IN_REPAYMENT → SETTLED / TERMINATED
```
| 狀態 | 意義 | 可執行動作（限主辦） |
|---|---|---|
| `DRAFT` | 建立中，主辦代填明細、設方案比例、邀請其他債權行 | 編輯明細、設定 `planRatio`、邀請 CO_BANK、發布 |
| `PENDING_CONFIRMATION` | 已發布，待各其他債權行確認 | 修正被回報異議（DISPUTED）的資料 |
| `IN_REPAYMENT` | 全數確認、方案生效，逐月更新（停留最久） | 登記還款、結清、毀諾終止 |
| `SETTLED` | 已結清 | — |
| `TERMINATED` | 毀諾／終止 | — |

其他債權行的確認狀態：`NOT_REQUIRED`（主辦本身）／`PENDING`／`CONFIRMED`／`DISPUTED`。

### 角色（RBAC）
- `ADMIN` 平台管理員：帳號建立／啟用碼／密碼重置、機構啟用管理、稽核、全案可見。
- `BANK_STAFF` 銀行人員：**角色因案動態認定**——建立案件者所屬銀行即該案「最大債權行（主辦，MAIN）」可編輯；受邀者為「其他債權行（CO_BANK）」僅檢視＋確認／異議。
- `PLATFORM_AUDITOR` 平台稽核：全案唯讀＋稽核，並為唯一可見 `internalTotal`（內部總額）者。
> 帳號狀態僅三種：`PENDING_ACTIVATION`／`ACTIVE`／`SUSPENDED`。（舊 `VIEWER` 角色已移除。）

## 三、四大流程

**1. 帳號啟用（正式區）**：admin 建帳號 → `PENDING_ACTIVATION` + 啟用碼 → 外部管道交付 → 使用者登入頁輸入啟用碼當密碼 → 切啟用模式設新密碼＋勾選個資同意 → `ACTIVE` 自動登入。（Demo 帳號已預設 `ACTIVE`，密碼 `Demo@1234`。）

**2. 最大債權行（主辦）**：建立案件（選法院＋填文號，`DRAFT`）→ 代填各行債權明細（`CreditItem`）→ 設還款計畫（月付金／期數／起始月）與各行 `planRatio`（手動、加總＝1）→ 邀請其他債權行 → **發布**（`PENDING_CONFIRMATION`，凍結主辦自身金額）。發布後 `planRatio` 鎖定，主辦僅能修正被異議的資料。

**3. 其他債權行**：收通知 → 檢視自家債權明細 → **確認**（凍結該行 `confirmedClaimAmount`）或**回報異議**（`DISPUTED` + 理由，待主辦修正後重新確認）。全數確認 → 案件轉 `IN_REPAYMENT`、寫 `confirmedAt` 與 `totalDebtAmount`。

**4. 逐月還款**：主辦每期只輸入 `period`（YYYY-MM）+ `actualReceivedTotal` → 系統依 `planRatio` 產生每行 `RepaymentAllocation`（`plannedAmount`＝月付×比例、`actualAmount`＝實收×比例）；**尾差記入主辦** `roundingAdjustment`，有尾差時 `hasRoundingAdjust=true`（前端提醒）。對照表（即算不落地）：剩餘債務＝`confirmedClaimAmount`−累計實際；計畫完成率＝Σ實際／Σ應還；債權回收率＝Σ實際／`confirmedClaimAmount`。主辦另可 `SETTLED` 結清或 `TERMINATED` 毀諾終止。

> 各角色逐步操作與測試腳本見 [`MANUAL.md`](../MANUAL.md)。

## 四、如何執行（本機）

需求環境：**Node.js 20+**、**Docker Desktop**。

### 方式一：本機開發（開發最快）
```bash
# 1) 啟動資料庫（Docker，Postgres 對外埠 5544）
cd backend && docker compose up -d

# 2) 安裝相依、套用 migration 與種子（首次或重置資料時）
npm install
npx prisma migrate deploy
npm run prisma:seed          # SEED_MODE 預設 demo

# 3) 啟動後端 API（http://localhost:4000，tsx watch 熱重載）
npm run dev

# 4) 另開終端，回專案根目錄啟動前端
cd .. && npm install && npm run dev   # http://localhost:5173（Vite HMR）
```
瀏覽器開 **http://localhost:5173**，以第八節 Demo 帳號登入。前端 API 位址由 `VITE_API_BASE` 決定（用 `??` 解析，空字串代表同源 `/api`），未設定時預設 `http://localhost:4000`。

### 方式二：全棧 Docker（本機驗收）
```bash
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --build
```
> 🔑 **專案名 `-p` 務必固定為 `dataexchange`**；同一台機器只跑這一組，否則會建到不對外的空殼 stack。
> dev 與 fullstack 讀同一份原始碼、但資料庫 volume 各自獨立（正常隔離）。

**改了原始碼要讓線上生效**（前端會編譯進映像）：
```bash
# 改前端（src/）→ 重建 web
docker compose -f docker-compose.fullstack.yml -p dataexchange build --no-cache web
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --force-recreate web
# 改後端（backend/）→ 重建 api
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --build api
```

## 五、部署與 TLS／HTTPS（staging 現況）

### 5.1 現況
- **Staging 網域**：`debit-ex-platform-staging.baasinnovation.com` → **OCI 主機 IP `207.211.153.165`**（DNS A 記錄已生效）。
- **HTTPS**：由 Caddy 向 **Let's Encrypt** 自動申請憑證（HTTP-01 challenge 走 80 埠驗證，之後 80→443 轉址）。
- **同源呼叫**：前端 build 帶 `VITE_API_BASE=""`，以同源 `/api` 呼叫後端，經 Caddy 反向代理，故不會有 CORS 問題。

### 5.2 compose 已內建網域預設（非機密，隨 git 同步）
`docker-compose.fullstack.yml` 已把「網域／HTTPS 模式」設為預設值，機密仍留 OCI 的 `.env`：

| 設定 | 位置 | 預設值 |
|---|---|---|
| `DOMAIN`（Caddy） | compose `caddy.environment` | `debit-ex-platform-staging.baasinnovation.com` |
| `CORS_ORIGIN`（後端） | compose `api.environment`（由 `PUBLIC_ORIGIN` 帶入） | `https://debit-ex-platform-staging.baasinnovation.com` |

> 皆保留 `${VAR:-預設}` 形式：`.env` 可覆寫。要改回 IP/HTTP：於 `.env` 設 `DOMAIN=:80` 且 `PUBLIC_ORIGIN=http://<公網IP>`。

### 5.3 `.env` 與機密（clone 後**必須**手建）

> ⚠️ **`.env` 不在 git 裡**（被 `.gitignore` 的 `.env` / `.env.*` 擋著），`git clone` 或 `git pull` **都不會**取得它——這是刻意的，避免機密外流到 GitHub。因此**每一台部署主機都要在 clone 後於本地端自行建立 `.env`**。

**`JWT_SECRET` 為必填（fail-fast 設計）**：compose 已移除其公開預設值，若 `.env` 未設定 `JWT_SECRET`，`docker compose up` 會**當場報錯、容器起不來**（訊息：「必填：請在 .env 設定 JWT_SECRET」）。這是為了杜絕「沿用公開預設金鑰、服務照跑但權杖可被偽造」的隱形風險。

| 變數 | 必要性 | 說明 |
|---|---|---|
| `JWT_SECRET` | **必填** | 未設定 → 容器啟動失敗。產生：`openssl rand -base64 48` |
| `DB_PASSWORD` | 選填 | 未設定用 `apppass`（DB 未對外開埠，風險中等）。**變更需 `down -v` 重建**，否則與既有 volume 密碼不符而連不上 |
| `SEED_MODE` | 選填 | `demo`（預設）／`production`；僅首次建庫生效（見 5.7） |
| `DOMAIN`／`PUBLIC_ORIGIN` | 選填 | staging 沿用 compose 預設網域者可不寫；換網域或改 IP/HTTP 時才填 |

**clone 後建立 `.env` 的最小步驟：**
```bash
cp .env.production.domain.example .env     # 以範本為底
openssl rand -base64 48                      # 產生金鑰，貼到 .env 的 JWT_SECRET=
# 編輯 .env：填入 JWT_SECRET；staging 沿用預設網域者，刪除 DOMAIN / PUBLIC_ORIGIN 兩行
```
> 最低限度：`.env` 內至少要有一組有效的 `JWT_SECRET`，否則無法啟動。

### 5.4 OCI 全新資料重建（GitHub 同步 → clone → 重建）
在 OCI 主機依序執行（**「全新資料」＝連 Docker volume 一起清**）：
```bash
# 0) 於舊資料夾內清掉舊容器 + 舊 volume（pgdata / caddy 憑證全清）
docker compose -f docker-compose.fullstack.yml -p dataexchange down -v

# 1) 刪舊資料夾、重新 clone 新版
cd ~ && rm -rf <舊資料夾> && git clone <repo URL> <資料夾> && cd <資料夾>

# 2) 建 .env（clone 不含；至少設 JWT_SECRET / DB_PASSWORD / SEED_MODE）
cp .env.production.domain.example .env   # 再編輯；staging 沿用預設網域者刪除 DOMAIN/PUBLIC_ORIGIN 兩行

# 3) 放行 443（80 保持開；OCI 兩層防火牆都要）
sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT && sudo netfilter-persistent save
#   OCI 主控台 Security List / NSG 亦須 Ingress 放行 TCP 443

# 4) 建置並啟動（fresh clone 一定要 --build）
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --build

# 5) 驗證
docker logs dataexchange-caddy-1 --tail 50    # 應見 certificate obtained、無 ACME error
docker logs dataexchange-api-1 --tail 30      # 應見 migrate deploy + seed 完成
curl -I https://debit-ex-platform-staging.baasinnovation.com/
```
**注意事項**
- `rm 資料夾` **不會**刪 Docker volume（pgdata/caddy 憑證存於 Docker 儲存區，依 `-p dataexchange` 命名）；要全新資料**必須** `down -v`。
- 憑證會重新申請；**勿短時間反覆 `down -v` 重來**，會撞 Let's Encrypt 速率限制（同網域每週 50 張、每小時 5 次失敗）。
- 重建後 admin 首次密碼為 `Demo@1234`，**立即以「使用者與權限管理 → 對自己發重置碼」改為強密碼**。

### 5.5 部署順序鐵則
**先確認 DNS 生效，再切 `DOMAIN`／申憑證**。驗證：`dig +short @8.8.8.8 debit-ex-platform-staging.baasinnovation.com` 回 `207.211.153.165` 才算。

### 5.6 IP／HTTP 後備（無網域時）
若改用純 IP、無網域：`.env` 設 `DOMAIN=:80`、`PUBLIC_ORIGIN=http://<公網IP>`，只放行 80 埠，瀏覽器開 `http://<公網IP>`。（Let's Encrypt 不發憑證給裸 IP，故此情境走 HTTP。）

### 5.7 兩種資料模式：Demo 與 Production（差異與啟動）

系統以環境變數 `SEED_MODE` 決定「首次建立資料庫」時要塞哪些種子資料。**兩種模式共用同一套程式碼與 schema，差別只在初始資料**。

| 項目 | `SEED_MODE=demo`（**預設**） | `SEED_MODE=production` |
|---|---|---|
| 用途 | 展示／測試流程 | 對外正式／乾淨起始 |
| 銀行 35／法院 23 主檔 | ✅ 建立（啟用 012/808/812/PLATFORM、TPD/SLD） | ✅ 建立（相同） |
| admin 帳號 | ✅ `admin@platform-demo.local`（密碼 `Demo@1234`） | ✅ 同左（密碼 `Demo@1234`） |
| 其他示範帳號 | ✅ 稽核＋3 家銀行承辦＋1 待啟用（密碼皆 `Demo@1234`，啟用碼 `ACT-DEMO-808`） | ❌ 不建立 |
| 示範案件 | ✅ 6 件（涵蓋全部 5 狀態） | ❌ 不建立 |
| 其餘帳號如何產生 | — | 一律由 admin 建立＋啟用碼啟用 |

> ⚠️ **`SEED_MODE` 只在「資料庫首次建立（空庫）」時生效。** 種子為 upsert（冪等）、且案件有防重（`case.count()>0` 即略過），因此對**已存在資料的庫改 `SEED_MODE` 不會生效、也不會清除舊資料**。要換模式必須**清空資料庫 volume** 後重建。

**啟動 Demo（預設，不必特別設定）：**
```bash
# .env 至少要有 JWT_SECRET；SEED_MODE 不寫即為 demo
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --build
```

**啟動 Production（乾淨起始）：**
```bash
# 於 .env 設 SEED_MODE=production；若該庫先前已用 demo 建過，須先清 volume：
docker compose -f docker-compose.fullstack.yml -p dataexchange down -v   # ⚠️ 清空資料庫（與憑證）
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --build
```

**兩模式共通的上線硬化（尤其對外站）：**
- **立即更改 admin 預設密碼**（`Demo@1234`）：admin 登入 → 使用者與權限管理 → 對自己「發重置碼」→ 設強密碼。
- demo 對外時，`admin@platform-demo.local / Demo@1234` 這組**已寫在 README／MANUAL**（等同公開帳密），對外站請務必改密碼或改用 production，或於 Caddy 前加存取限制。
- 確認目前模式：`curl -s https://<網域>/health` 觀察 `users` 筆數（demo 有 6 筆帳號、production 為 1 筆 admin）。

## 六、後端 API 一覽（`/api` 前綴由 `server.ts` 分模組掛載）

> 授權：「JWT」＝需有效權杖；角色＝另需該角色；「主辦／CO_BANK」＝依該案身分動態判定。全域限流 100 次／分，敏感端點另有覆寫。

### 認證 `auth.ts`（`/api/auth`）
| 方法 | 路徑 | 用途 | 授權 | 限流 |
|---|---|---|---|---|
| GET | `/active-banks` | 登入頁用的啟用中銀行清單 | 公開 | 全域 |
| POST | `/login` | 三層驗證登入；偵測 PENDING_ACTIVATION 回 `activationRequired` | 公開 | 10 次／5 分 |
| POST | `/activate` | 啟用帳號：設密碼＋個資同意，自動登入 | 公開（憑碼驗證） | 20 次／10 分 |
| GET | `/me` | 目前登入者資料 | JWT | 全域 |

### 密碼重置 `passwordReset.ts`（`/api`）
| 方法 | 路徑 | 用途 | 授權 | 限流 |
|---|---|---|---|---|
| POST | `/auth/request-password-reset` | 使用者申請（通用回應） | 公開 | 5 次／10 分 |
| POST | `/auth/reset-password` | 憑重置碼設新密碼（≥8） | 公開（憑碼驗證） | 20 次／10 分 |
| GET | `/password-reset-requests` | 待處理申請清單 | ADMIN | 全域 |
| POST | `/password-reset-requests/:id/issue` | 對申請核發重置碼 | ADMIN | 全域 |
| POST | `/users/:userId/issue-reset` | 主動替帳號核發重置碼 | ADMIN | 全域 |

### 案件 `cases.ts`（`/api/cases`，整檔需 JWT）
| 方法 | 路徑 | 用途 | 授權 |
|---|---|---|---|
| GET | `/` | 依角色／銀行列出可見案件 | JWT（依銀行縮限） |
| POST | `/` | 建立案件（建立者所屬行＝主辦） | BANK_STAFF（非 PLATFORM） |
| GET | `/:caseId` | 案件詳情（套用可視範圍） | 主辦／參與行／ADMIN／AUDITOR |
| POST | `/:caseId/participants` | 邀請其他債權行（CO_BANK） | 該案主辦，`DRAFT` |
| PUT | `/:caseId/participants/:bankCode/items` | 代填某行債權明細 | 該案主辦 |
| PUT | `/:caseId/plan` | 設還款計畫＋各行 `planRatio`（加總＝1） | 該案主辦，`DRAFT` |
| POST | `/:caseId/publish` | 發布（凍結主辦金額、通知各行） | 該案主辦，`DRAFT` |

### 案件流程 `caseFlow.ts`（`/api/cases`，整檔需 JWT）
| 方法 | 路徑 | 用途 | 授權 |
|---|---|---|---|
| POST | `/:caseId/confirm` | CO_BANK 確認（凍結該行 `confirmedClaimAmount`；全數確認→`IN_REPAYMENT`） | 該案 CO_BANK |
| POST | `/batch-confirm` | 批次確認多案 | 各案 CO_BANK |
| POST | `/:caseId/dispute` | 回報異議（`reason`） | 該案 CO_BANK |
| POST | `/:caseId/repayments` | 登記本期實收（依比例自動攤提） | 該案主辦，`IN_REPAYMENT` |
| GET | `/:caseId/repayments` | 還款對照表（計畫 vs 實際） | 主辦／參與行／ADMIN／AUDITOR |
| POST | `/:caseId/settle` | 結清 | 該案主辦，`IN_REPAYMENT` |
| POST | `/:caseId/terminate` | 毀諾／終止（`reason`） | 該案主辦，`IN_REPAYMENT` |

### 使用者管理 `usersAdmin.ts`（`/api/users`，整檔 ADMIN）
| 方法 | 路徑 | 用途 |
|---|---|---|
| GET | `/?status=` | 使用者清單（可篩狀態） |
| GET | `/:userId/audit` | 該使用者稽核軌跡 |
| POST | `/` | 建立帳號（PENDING_ACTIVATION）＋回傳啟用碼 |
| POST | `/:userId/issue-activation` | 重新核發啟用碼 |
| POST | `/:userId/suspend`｜`/reactivate`｜`/unlock` | 停用／復用／解除登入鎖定 |

### 機構主檔
- `banks.ts`（`/api/banks`，需 JWT）：`GET /?activeOnly=` 清單；`PATCH /:bankCode` 切換 `isActive`（**ADMIN**）。
- `courts.ts`（`/api/courts`，需 JWT）：`GET /?activeOnly=` 清單；`PATCH /:courtCode` 切換 `isActive`（**ADMIN**）。

### 其他
- `dashboard.ts`：`GET /api/dashboard/summary` — 依角色回統計與待辦（ADMIN：待啟用數／待重置數／各狀態案件數；AUDITOR：各狀態案件數；BANK_STAFF：`asMain` 與 `asCoBank` 待辦）。需 JWT。
- `notifications.ts`（需 JWT，僅本人）：`GET /api/notifications`（最多 100＋unreadCount）、`POST /:id/read`、`POST /read-all`。
- `audit.ts`（ADMIN／PLATFORM_AUDITOR）：`GET /api/audit-logs`（可 `?actionType=&bankCode=&from=&to=&limit=`，預設 200、上限 500）。
- `server.ts`：`GET /health` — 健康檢查，回 db 連線與 bank／user 筆數（免驗證）。
