## 版本重點（v0.3 相對 v0.2）

- **流程改版為「債權申報與彙整」**：由 v0.2 的「主辦代填＋還款管理」改為 **各行自填自己的債權 → 封閉申報、全員確認 → 一次揭露、產出債權彙整表 → 主辦回報成立／不成立（終態鎖死）**。
- **移除還款管理**：`planRatio`／逐月攤提／`RepaymentPeriod`／`RepaymentAllocation`／`IN_REPAYMENT`／`SETTLED`／`TERMINATED` 全數移除；不處理法定期限；債務人與法院全程線下。
- **可視性改為兩階段＋平台全盲**：封閉申報期各行只見自己；全員確認揭露後參與行互見。**平台管理員只見狀態與進度、不見任何金額**；平台稽核可見全部。`internalTotal` 已移除。
- **新增疑義迴圈與版本化**：揭露後任一參與行可標記疑義 → 全案退回、輪次（round）+1、全員重新確認；新增 `CaseDoubt`（疑義）與 `DeclarationSnapshot`（每輪揭露快照）。
- **終態鎖死**：`ESTABLISHED`／`NOT_ESTABLISHED` 為終態、不可更正、`(courtCode,docNumber)` 不得以同文號新建；回報採兩段式確認防呆。
- **部署／TLS 不變**：staging 網域、Let's Encrypt 自動 HTTPS、compose 網域預設、`.env` 機密與 `JWT_SECRET` fail-fast 皆延續 v0.2（見第五節）。
- **資料庫遷移基線更新**：以全新 `20260728000000_v03_init` 取代舊 `v2_init`（v0.3 為破壞性模型變更，重建須清空 volume）。

## 一、一句話總覽

跨銀行「前置調解**債權申報與彙整**」平台，前後端整合的**全棧系統**：

> 主辦（最大債權行）依法院公文建立案件（選法院＋填文號）並**邀請**其他債權行 → 發布 → **各行（含主辦）自填自己的債權明細並確認**（封閉申報，只看得到自己的）→ **全員確認後一次揭露、產出債權彙整表**（參與行互見）→ 主辦**線下與債務人確認後回報成立／不成立**（終態）。揭露後有疑義可退回全員重新確認。**無還款、無時限。**

帳號採**管理員建立＋啟用碼啟用制**，資料存於 **PostgreSQL**，權限一律由**後端強制（Server-side RBAC）**；前端無任何本地資料層，全部呼叫後端 REST API。

> ⚠️ **關於「平台全盲」**：現行為集中式應用，「平台管理員不見金額」是**應用層 RBAC** 所擋，營運主機／DB 端技術上仍可讀明文；**密碼學層級的真全盲屬 Fabric 版目標設計**（見 `feat/fabric-poc` 分支與 [`docs/風險與合規檢視.md`](./風險與合規檢視.md)）。對外說明時勿以現行系統宣稱「平台看不到資料」。

## 二、技術架構

| 層 | 技術 | 位置 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite 5 + Tailwind 3 + React Router 6 + Zustand | `src/` |
| 前端資料存取 | 統一經 `src/services/api.ts`（`apiFetch`，自動附 JWT） | `src/services/` |
| 後端 | Fastify 4 + Prisma 5 + Zod（`@fastify/jwt`、bcryptjs、`@fastify/rate-limit`、`@fastify/cors`） | `backend/src/` |
| 資料庫 | PostgreSQL 16 | Docker |
| 部署 | 本機開發（Vite + tsx）或全棧 Docker（db + api + web + Caddy 反向代理／自動 HTTPS） | `docker-compose.fullstack.yml` |

### 認證與帳號模型（啟用碼制，與 v0.2 相同）
- **登入**：銀行代碼 + Email + 密碼三層驗證 → 回傳 JWT（效期 **8 小時**，payload 含 `userId / role / bankCode / name`）。失敗訊息一律通用，避免帳號列舉。
- **帳號啟用**：管理員建立帳號（狀態 `PENDING_ACTIVATION`、無密碼）並產生一次性**啟用碼**（雜湊儲存、效期 **3 天**，由外部管道遞送，免 SMTP）。使用者於登入頁「選銀行＋Email＋啟用碼當密碼」→ 後端回 `activationRequired` → 前端切換為**啟用模式**：設定新密碼（≥8 碼）＋**勾選個資使用同意** → 帳號轉 `ACTIVE`。
- **登入鎖定**：僅密碼錯時累計，連續 **5 次** → 鎖定 **15 分鐘**；管理員可手動解鎖。
- **密碼重設**：使用者送出申請 → 管理員核發一次性重置碼 → 使用者以重置碼設新密碼。

### 案件狀態機（v0.3）
```
DRAFT → PENDING_CONFIRMATION → PENDING_OUTCOME → ESTABLISHED / NOT_ESTABLISHED
                    ▲                   │
                    └── 疑義退回(round+1)─┘
        （僵局出口：PENDING_CONFIRMATION → NOT_ESTABLISHED）
```
| 狀態 | 意義 | 主要動作 |
|---|---|---|
| `DRAFT` | 主辦起案＋邀請，尚未發布 | 主辦：填本行債權、邀請/移出參與行、發布 |
| `PENDING_CONFIRMATION` | 封閉申報中：各行自填並確認自己（含主辦） | 各行：填本行、確認/撤回、拒絕參與；主辦：移出、回報不成立（僵局） |
| `PENDING_OUTCOME` | 全員確認、已揭露、產出債權彙整表 | 主辦：兩段式回報成立/不成立；參與行：標記疑義（退回重確認） |
| `ESTABLISHED` | 已回報成立（終態、鎖死） | — |
| `NOT_ESTABLISHED` | 已回報不成立（終態、鎖死，附理由） | — |

各參與行（含主辦）的確認狀態僅兩種：`PENDING`／`CONFIRMED`。移出／拒絕以 `removedAt`＋`removalKind`（`REJECTED_SELF`／`REMOVED_BY_MAIN`）標記，保留紀錄可被重新邀請復原。

### 角色與可視性（RBAC）
- `ADMIN` 平台管理員：帳號建立／啟用碼／密碼重置、機構啟用管理、稽核。**案件只見狀態與進度，不見任何金額或明細**（金額欄一律回 `null`）。
- `BANK_STAFF` 銀行人員：**角色因案動態認定**——建立案件者所屬銀行即該案「主辦（MAIN）」；受邀者為「其他債權行（CO_BANK）」。**主辦與各行都是需自填、自我確認的參與行。**
- `PLATFORM_AUDITOR` 平台稽核：全案唯讀，**全程可見全部**（含封閉申報期間各行明細、彙整表與**各行對內債權**）。
> 封閉申報期的可視性：各行**只見自己的**數字＋確認進度＋參與行名單；**揭露後**參與行互相可見。帳號狀態三種：`PENDING_ACTIVATION`／`ACTIVE`／`SUSPENDED`。

## 三、主要流程

**1. 帳號啟用（正式區）**：admin 建帳號 → `PENDING_ACTIVATION` + 啟用碼 → 外部管道交付 → 使用者登入頁輸入啟用碼當密碼 → 切啟用模式設新密碼＋勾選個資同意 → `ACTIVE`。（Demo 帳號已預設 `ACTIVE`，密碼 `Demo@1234`。）

**2. 主辦起案與發布**：建立案件（選法院＋填文號，`DRAFT`；名單依法院公文線下取得後輸入）→ 填**本行**債權明細（`CreditItem`）→ 邀請其他債權行 → **發布**（`PENDING_CONFIRMATION`）。可移出參與行、重新邀請已移出者。

**3. 封閉申報與確認（各行，含主辦）**：各行填**自己的**債權明細並**確認**（凍結該行 `confirmedClaimAmount` 快照）；確認前僅本行（＋稽核）可見。確認後、揭露前可**撤回**再改。CO_BANK 若非本案債權人可**拒絕參與**（自行移出、附理由、留稽核）。

**4. 揭露與彙整**：**全員（含主辦）皆確認** → 系統自動**一次揭露**：寫 `disclosedAt`、凍結 `consolidatedTotal`、為每一（未移出）參與行建立當輪 `DeclarationSnapshot`，狀態轉 `PENDING_OUTCOME`。前端據各行明細本地拼接**債權彙整表**（v0.35 重設計，**表頭以法院＋公文文號辨識、不含債務人個資**）：
   - **表一（全體彙整）**：全案**依 6 類債權**（信用卡／現金卡／信用貸款／保證／繼承／其他）加總的本金/利息/違約金/其他/總額＋全案總計。
   - **表二（各行明細）**：每一參與行**依債權種類**列出金額與該行小計（寬表水平捲動）。
   - 🔒 **對內債權（C-1）**：`internalPrincipal`／`internalInterest` 及即算本息總和，**僅本行與稽核可見**（`canSeeInternal = 稽核 或 本行`；他行、admin 皆不回傳），永不與他行共享。

**5. 疑義迴圈**：揭露後任一參與行可**標記疑義**（`CaseDoubt`，理由必填、可指向某行）→ 全案退回 `PENDING_CONFIRMATION`、`round+1`、全員確認狀態重置；再次全員確認 → 再次揭露。組成變更（揭露後移出/拒絕）比照疑義退回。

**6. 回報結果（主辦）**：主辦線下與債務人確認後，經**兩段式確認**回報 `ESTABLISHED` 或 `NOT_ESTABLISHED`（後者附理由）→ 終態鎖死。僵局時主辦亦可於 `PENDING_CONFIRMATION` 逕行回報不成立作為出口。

> 各角色逐步操作與測試腳本見 [`MANUAL.md`](../MANUAL.md)。

## 四、如何執行（本機）

需求環境：**Node.js 20+**、**Docker Desktop**。

### 方式一：本機開發（開發最快）
```bash
# 1) 啟動資料庫（Docker，Postgres 對外埠 5544）
cd backend && docker compose up -d

# 2) 安裝相依、套用 migration 與種子（首次或重置資料時）
npm install
npx prisma migrate deploy
npm run prisma:seed          # SEED_MODE 預設 demo

# 3) 啟動後端 API（http://localhost:4000，tsx watch 熱重載）
npm run dev

# 4) 另開終端，回專案根目錄啟動前端
cd .. && npm install && npm run dev   # http://localhost:5173（Vite HMR）
```
瀏覽器開 **http://localhost:5173**，以第八節 Demo 帳號登入。前端 API 位址由 `VITE_API_BASE` 決定（用 `??` 解析，空字串代表同源 `/api`），未設定時預設 `http://localhost:4000`。

### 方式二：全棧 Docker（本機驗收）
```bash
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --build
```
> ℹ️ 本節的 `--build` 僅適用於**本機**（開發機記憶體充足）。**部署主機一律不可 build**，見第五節開頭鐵則與 [`deploy/README.md`](../deploy/README.md)。
> 🔑 **專案名 `-p` 務必固定為 `dataexchange`**；同一台機器只跑這一組，否則會建到不對外的空殼 stack。
> dev 與 fullstack 讀同一份原始碼、但資料庫 volume 各自獨立（正常隔離）。

**改了原始碼要讓線上生效**（前端會編譯進映像）：
```bash
# 改前端（src/）→ 重建 web
docker compose -f docker-compose.fullstack.yml -p dataexchange build --no-cache web
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --force-recreate web
# 改後端（backend/）→ 重建 api
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --build api
```

> ⚠️ **v0.3 為破壞性資料模型變更**：由 v0.2 既有資料庫升級 v0.3 時，`migrate deploy` 會因基線 migration 更換而不相容；**須先 `down -v` 清空 volume 再重建**（見 5.4）。

## 五、部署與 TLS／HTTPS（staging 現況）

> ⛔ **鐵則：不得在部署主機上 build。** staging 主機為 `VM.Standard.E2.1.Micro`（1 OCPU / 954 MB），
> 容器內 `npm ci` + `vite build` 峰值需 1.5–2 GB，會把整台機器拖進重度 swap thrash（2026-09-10 實際發生，
> 連 sshd 都送不出 banner，最後以強制電源循環才恢復；資料靠 WAL 完整復原）。
> **例行升版一律使用 [`deploy/build-and-ship.sh`](../deploy/build-and-ship.sh)**（本機建置 → 傳送映像 → `up -d --no-build`）。
> 完整說明、兩個跨架構建置陷阱與回滾程序見 [`deploy/README.md`](../deploy/README.md)。

### 5.1 現況
- **Staging 網域**：`debit-ex-platform-staging.baasinnovation.com` → **OCI 主機 IP `207.211.153.165`**（DNS A 記錄已生效）。
- **HTTPS**：由 Caddy 向 **Let's Encrypt** 自動申請憑證（HTTP-01 challenge 走 80 埠驗證，之後 80→443 轉址）。
- **同源呼叫**：前端 build 帶 `VITE_API_BASE=""`，以同源 `/api` 呼叫後端，經 Caddy 反向代理，故不會有 CORS 問題。

### 5.2 compose 已內建網域預設（非機密，隨 git 同步）
`docker-compose.fullstack.yml` 已把「網域／HTTPS 模式」設為預設值，機密仍留 OCI 的 `.env`：

| 設定 | 位置 | 預設值 |
|---|---|---|
| `DOMAIN`（Caddy） | compose `caddy.environment` | `debit-ex-platform-staging.baasinnovation.com` |
| `CORS_ORIGIN`（後端） | compose `api.environment`（由 `PUBLIC_ORIGIN` 帶入） | `https://debit-ex-platform-staging.baasinnovation.com` |

> 皆保留 `${VAR:-預設}` 形式：`.env` 可覆寫。要改回 IP/HTTP：於 `.env` 設 `DOMAIN=:80` 且 `PUBLIC_ORIGIN=http://<公網IP>`。

### 5.3 `.env` 與機密（clone 後**必須**手建）

> ⚠️ **`.env` 不在 git 裡**（被 `.gitignore` 的 `.env` / `.env.*` 擋著），`git clone` 或 `git pull` **都不會**取得它——這是刻意的，避免機密外流到 GitHub。因此**每一台部署主機都要在 clone 後於本地端自行建立 `.env`**。

**`JWT_SECRET` 為必填（fail-fast 設計）**：compose 已移除其公開預設值，若 `.env` 未設定 `JWT_SECRET`，`docker compose up` 會**當場報錯、容器起不來**（訊息：「必填：請在 .env 設定 JWT_SECRET」）。

| 變數 | 必要性 | 說明 |
|---|---|---|
| `JWT_SECRET` | **必填** | 未設定 → 容器啟動失敗。產生：`openssl rand -base64 48` |
| `DB_PASSWORD` | 選填 | 未設定用 `apppass`（DB 未對外開埠）。**變更不需毀掉 volume**：於 DB 內執行 `ALTER USER app WITH PASSWORD '<新密碼>'`、同步更新 `.env`、再重啟 api 即可（先前文件誤載須 `down -v`，已更正）。⚠️ 預設值 `apppass` 尚未移除，屬待辦資安硬化項 |
| `SEED_MODE` | 選填 | `demo`（預設）／`production`；僅首次建庫生效（見 5.7） |
| `DOMAIN`／`PUBLIC_ORIGIN` | 選填 | staging 沿用 compose 預設網域者可不寫；換網域或改 IP/HTTP 時才填 |

**clone 後建立 `.env` 的最小步驟：**
```bash
cp .env.production.domain.example .env     # 以範本為底
openssl rand -base64 48                      # 產生金鑰，貼到 .env 的 JWT_SECRET=
# 編輯 .env：填入 JWT_SECRET；staging 沿用預設網域者，刪除 DOMAIN / PUBLIC_ORIGIN 兩行
```

### 5.4 OCI 全新資料重建（GitHub 同步 → 重建）
v0.3 升級或全新資料，**必須清 volume**。建議做法（保留 Caddy 憑證、只清 DB）：
```bash
cd <repo>                                    # 既有 clone 目錄
git fetch origin --tags && git checkout main && git pull origin main
test -f .env && grep -q '^JWT_SECRET=' .env && echo ".env OK"   # 確認機密還在
docker compose -f docker-compose.fullstack.yml -p dataexchange down   # 停容器、保留 volume
docker volume ls | grep dataexchange
docker volume rm dataexchange_pgdata          # 只清 DB volume（保留 caddy 憑證，避免重申 LE）
# 映像須事先以 deploy/build-and-ship.sh 送上主機；此處刻意用 --no-build（見本節開頭鐵則）
docker compose -f docker-compose.fullstack.yml -p dataexchange up -d --no-build
docker compose -f docker-compose.fullstack.yml -p dataexchange logs -f api   # 應見 v03_init 套用 + seed 完成
```
> 若要連憑證一起清（極少用），才用 `down -v`；**勿短時間反覆重來**，會撞 Let's Encrypt 速率限制（同網域每週 50 張、每小時 5 次失敗）。
> 重建後 admin 首次密碼為 `Demo@1234`，**立即以「使用者與權限管理 → 對自己發重置碼」改為強密碼**。

### 5.5 部署順序鐵則

## 九、資料模型與主鍵設計

- **資料模型（12 張表）**：`Bank`、`Court`、`User`、`AccessCode`、`PasswordResetRequest`、`Case`、`CaseParticipantBank`、`CreditItem`、**`CaseDoubt`**、**`DeclarationSnapshot`**、`Notification`、`AuditLog`。金額 `Decimal(21,4)`。
  - 相對 v0.2：**移除** `RepaymentPeriod`／`RepaymentAllocation`／`CaseParticipantBank.planRatio` 與 `Case` 的還款欄位；**新增** `CaseDoubt`（疑義 append-only）、`DeclarationSnapshot`（每輪揭露快照＝版本化）、`Case.round`／`disclosedAt`／`consolidatedTotal`／`outcomeReportedAt`／`notEstablishedReason`、`CaseParticipantBank.removedAt`／`removalKind`／`removalReason`。
  - **v0.35_TableChange（債權彙整表對齊）**：`ClaimType` 擴為 **6 類**（信用卡`CREDIT_CARD`／現金卡`CASH_CARD`／信用貸款`CREDIT_LOAN`／保證`GUARANTEE`／繼承`INHERITANCE`／其他`OTHER`）；`CreditItem` 新增**對內債權** `internalPrincipal`／`internalInterest`（本息總和＝兩者之和，即算不落地；**僅該行本身或稽核可見，永不對他行揭露＝C‑1**）；`Case` 新增 `mediationDate`（調解日期）、`notifiedDate`（通報日期，保留欄位、可空）。<br>「對外債權」四分項（本金/利息/違約金/其他費用）與 v0.3 相同、揭露後參與行互見。

- **主鍵（primary key）設計**：採「**代理主鍵＋業務唯一鍵**」雙軌。
  - **代理主鍵**：`Case.caseId`、`User.userId`、`CaseParticipantBank.participantId`、`CreditItem.itemId`、`CaseDoubt.doubtId`、`DeclarationSnapshot.snapshotId`、`AccessCode.codeId`、`Notification.notificationId`、`AuditLog.logId` 等，皆為 **`@default(cuid())`**——由 Prisma 在**應用層**產生的抗碰撞、URL-safe、具時間前綴的字串 ID（不需 DB 往返、不洩露筆數、索引局部性佳）。純內部關聯，不承載業務語意。
  - **業務唯一鍵**：案件對外辨識為複合唯一鍵 **`@@unique([courtCode, docNumber])`**（法院代碼＋法院公文文號），由主辦依法院公文線下輸入、系統不解析格式。此即「**結案後不得以同文號新建**」終態鎖死所依據之鍵（建案時 `findUnique({courtCode_docNumber})` 擋重複回 409）。其他複合唯一鍵：`CaseParticipantBank @@unique([caseId, bankCode])`。
  - **參考主檔自然鍵**：`Bank.bankCode`（3 碼機構代號）、`Court.courtCode`（法院代碼）直接作 `@id`。
  > Fabric 版上鏈時，`(courtCode,docNumber)` 因熵低、格式固定，**不直接上鏈**，而以**加鹽 HMAC 產生 caseRef commitment**（見 `docs/風險與合規檢視.md` T2／`Fabric 設計與 PoC 規劃.md`），避免平台字典枚舉真實案號。

- **遷移**：基線 `20260728000000_v03_init`（greenfield，取代舊 `v2_init`）＋以下**非破壞性**增量，皆**可直接 `migrate deploy`、不需清空 volume**：
  - `20260817000000_v035_table_change`：加 enum 值、加 `cases`/`credit_items` 欄位。
  - `20260825000000_v04a_item_rules`：`credit_items` 加 `claimTypeOther`＋**一類一筆唯一索引** `(participantId, claimType)`。建索引前先將既有重複種類**金額相加合併**再刪多餘列，避免既有資料使升級失敗。
  - `20260909000000_v04b_participant_guards`：`declaration_snapshots` 加 `excluded`／`removalKind`／`removalReason`，使每輪快照可還原「誰在、誰不在、為什麼」。
  - `20260910000000_v04d_case_edit_fields`：`AuditActionType` 加 `CASE_DELETED`；`cases` 加 `mediationTime`／`mediationPlace`／`interestCutoffDate`。
  - `20260910000001_v04e_secured_claims_reserved`：新增 `secured_credit_items` 表（有擔保債權，**僅保留結構、尚未啟用**）。
  - `20260911000000_v05a_audit_append_only`：`audit_logs` 於**資料庫層**設為僅可新增——statement-level 觸發器阻擋 `UPDATE` 與 `DELETE`。防的不是應用程式（應用層本來就只有 `create`／`findMany`），而是繞過應用層直接改動或抹除紀錄。副作用刻意保留：因 `audit_logs.userId` 外鍵為 `ON DELETE SET NULL`，「刪除使用者」會對稽核表產生 `UPDATE` 而被阻擋（目前無刪除使用者功能，且「有稽核歷史者不得被刪除」本身即為期望性質）。保留期限清理須明確暫時停用觸發器後執行（指令見 migration 檔註解）。
  已驗證七支 migration 自空庫依序重放並 seed 成功（即 OCI 升級之真實情境）。全棧後端映像啟動時自動 `prisma migrate deploy` + `prisma db seed`。
