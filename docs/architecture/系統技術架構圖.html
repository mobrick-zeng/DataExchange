橫切關注點
安全
  • JWT 無狀態驗證、bcrypt 密碼雜湊
  • Rate-limit、CORS 白名單、憑證自動更新
  • 可執行動作與可見範圍一律由後端把關
可視性治理（RBAC）
  • 平台全盲：管理員只見狀態，金額欄一律回 null
  • 稽核全見：全案唯讀，含各行明細與對內債權
  • C-1 對內債權：僅本行＋稽核可見，不與他行共享
  • 封閉→揭露：申報期各行只見自己，全員確認才揭露
稽核軌跡
  • AuditLog 記錄申報／確認／撤回／揭露／疑義／回報
  • 每輪揭露留 DeclarationSnapshot 快照，可回溯
終態鎖死
  • 結案（成立／不成立）為終態、兩段式防呆
  • 不可更正、不得以同文號新建

案件狀態機

DRAFT 草稿 ›發布› 封閉申報中 ›全員確認→揭露› 待回報 ›主辦線下回報› 成立 ／ 不成立
疑義迴圈：揭露後任一參與行可標記疑義 → 全案退回封閉申報、round + 1、全員重新確認
組成變更防護：主辦移出參與行或該行自行拒絕參與時，即使剩餘各行恰已全數確認，系統刻意不自動揭露；須由主辦另行執行 POST /:caseId/disclose 二次確認，使「排除某行」與「定案」成為兩個各自留痕的決定。已揭露後發生組成變更則一律退回重新確認。

資訊可視性閘門 — 同一支 GET /api/cases/:caseId，五種身分五種回應

可視性不是由前端隱藏，而是後端在組裝回應時逐欄位決定：不可見的欄位回傳 null， 他行的數字從未離開伺服器。整份案件只有一個「閘門」——全員確認後的揭露；在此之前與之後，是兩個不同的資訊世界。

平台全盲
平台管理員負責帳號、銀行與法院主檔的維運，所有金額欄位一律回傳 null——不是介面不顯示，而是資料不出庫。
稽核全見
平台稽核可讀取全部欄位以履行查核義務，但為唯讀：不得建案、不得填報、不得確認、不得回報結果。
對內債權（C-1）
internalPrincipal / internalInterest 僅該行本身與稽核可見，即使揭露後亦不對他行釋出；不進入彙整表總額。
寫入面的對稱限制：各行只能寫自己的明細——PUT /:caseId/my-items 的寫入對象由 JWT 內的 bankCode 反查取得， 不接受前端指定參與者，因此「代他行填報」在結構上不可能發生。已確認者須先撤回確認才能修改；已揭露者須經疑義退回才能修改。
