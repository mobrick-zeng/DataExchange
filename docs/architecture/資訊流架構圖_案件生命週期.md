# 資訊流架構圖 — 案件生命週期

> 前置調解債權交換平台　·　v0.5
> 一件案子從建立到結案，資訊如何在前後端之間流動。
> 圖像版（資訊更密、可列印）：[`資訊流架構圖_案件生命週期.html`](./資訊流架構圖_案件生命週期.html)

---

## 最本質的一句話

**銀行與銀行之間沒有任何直接連線。** 所謂「案件在系統間傳遞」，實際上是各行前端各自呼叫**同一個後端 API**、讀寫**同一個資料庫**。

| | |
|---|---|
| **PULL，不是 PUSH** | 平台不對銀行端送件，沒有 webhook、不需要銀行端開放任何 inbound。所有「通知」只是資料庫寫一列，對方前端每 30 秒輪詢才拉到。 |
| **過濾在後端發生** | 他行的數字從未離開伺服器。同一支 `GET /api/cases/:caseId`，五種身分拿到五種內容——不是前端隱藏。 |

```mermaid
flowchart LR
    A["A 行瀏覽器"] -- "HTTPS" --> API["後端 API"]
    B["B 行瀏覽器"] -- "HTTPS" --> API
    API --> DB[("PostgreSQL")]
    A x--x B
    linkStyle 3 stroke:#be123c,stroke-width:2px
```

> 兩行之間那條打叉的紅線代表**不存在的連線**：無檔案交換、無點對點通道。

## 案件生命週期時序

```mermaid
sequenceDiagram
    autonumber
    participant A as A 行（主辦）瀏覽器
    participant B as B 行（參與行）瀏覽器
    participant API as 後端 API（Caddy → Fastify）
    participant DB as PostgreSQL

    rect rgb(245,247,250)
    Note over A,DB: 階段 0 — 身分建立
    A->>API: POST /api/auth/login
    API->>DB: 比對 bcrypt 雜湊
    API-->>A: JWT（HS256）
    Note right of API: 之後每次請求都從 JWT 取出<br/>userId / bankCode / role。<br/>前端傳來的身分一律不採信。
    end

    rect rgb(239,246,255)
    Note over A,DB: 階段 1 — 建案與邀請（主辦單方作業）
    A->>API: POST /api/cases
    API->>DB: 建 Case（DRAFT）＋主辦自動建為 MAIN 參與行
    Note right of DB: 唯一鍵 (courtCode, docNumber) 擋重複建案<br/>不儲存個資，以法院＋文號識別

    A->>API: POST /:caseId/participants（邀請 B）
    API->>DB: 建 B 為 CO_BANK（PENDING）＋寫 Notification
    Note over B: 邀請即可見——B 自此讀得到案件<br/>基本資料，但看不到任何金額

    A->>API: POST /:caseId/publish
    Note right of API: 前置檢查：至少已邀請一家其他債權行
    API->>DB: status → PENDING_CONFIRMATION＋逐一寫通知
    end

    rect rgb(245,243,255)
    Note over A,DB: 階段 2 — 封閉申報（各行自填、互不可見）
    B->>API: PUT /:caseId/my-items
    API->>DB: B 的 CreditItem 整批取代（一債權種類僅一列）
    A->>API: PUT /:caseId/my-items（主辦也必須自填，非代填）
    API->>DB: A 的 CreditItem 整批取代
    Note right of API: 寫入對象由 JWT 的 bankCode 反查，<br/>不接受前端指定 participantId<br/>→ 代他行填報在結構上不可能

    B->>API: POST /:caseId/confirm
    Note right of API: 前置檢查：未填報者不得確認<br/>（避免以 0 元誤確認）
    API->>DB: confirmationStatus → CONFIRMED、凍結該行金額
    API->>DB: 通知主辦「B 已確認」
    Note over A: 主辦只知道 B 確認了，<br/>仍讀不到 B 的任何數字（回應為 null）
    end

    rect rgb(255,251,235)
    Note over A,DB: 階段 3 — 揭露閘門（整條流程唯一的資訊釋放點）
    A->>API: POST /:caseId/confirm（最後一家）
    Note right of API: 全員皆已確認 → maybeDisclose()<br/>於同一個請求內同步觸發<br/>無排程器、無訊息佇列
    API->>DB: 凍結 consolidatedTotal
    API->>DB: 為每一家寫 DeclarationSnapshot（含該輪被排除者）
    API->>DB: status → PENDING_OUTCOME＋通知全員
    Note over A,B: 閘門開啟：自此參與行才讀得到他行明細與彙整表<br/>但對內債權（C-1）永不對他行開放
    end

    rect rgb(255,241,242)
    Note over A,DB: 階段 4 — 疑義迴圈（可重複多輪）
    B->>API: POST /:caseId/doubt（附理由）
    API->>DB: 建 CaseDoubt、round + 1、清空彙整總額
    API->>DB: 全員確認狀態重置、status → PENDING_CONFIRMATION
    Note right of DB: 各行明細保留，僅需修改後重新確認<br/>上一輪快照不刪除——每輪皆可完整還原
    end

    rect rgb(236,253,245)
    Note over A,DB: 階段 5 — 結案
    A->>API: POST /:caseId/report（established＋confirm=true）
    Note right of API: 回報「成立」須已揭露<br/>回報「不成立」須填理由
    API->>DB: status → ESTABLISHED / NOT_ESTABLISHED（終態鎖死）
    end

    rect rgb(248,250,252)
    Note over A,DB: 貫穿全程 — 通知是「拉」的
    loop 每 30 秒
        A-->>API: GET /api/notifications
        B-->>API: GET /api/notifications
    end
    Note over A,B: 上述每一個「通知」只是在資料庫寫一列；<br/>直到對方瀏覽器來拉，資訊才真正抵達
    end
```

## 例外：組成變更後不自動揭露

若主辦以 `POST /:caseId/participants/:bankCode/remove` **移出**某行、或某行**自行拒絕參與**，而使剩餘各行恰好全數確認，系統**刻意不自動揭露**。

```mermaid
flowchart TB
    R["主辦移出某行<br/>或某行自行拒絕參與"] --> Q{"案件是否已揭露？"}
    Q -- "已揭露" --> RE["組成變更 → 退回全員重新確認<br/>round + 1"]
    Q -- "未揭露" --> C{"剩餘各行是否全數確認？"}
    C -- "否" --> W["維持封閉申報中"]
    C -- "是" --> RD["回應 readyToDisclose: true<br/>但不自動揭露"]
    RD --> M["須由主辦另行執行<br/>POST /:caseId/disclose（confirm=true）"]
    style RD fill:#fffbeb,stroke:#b45309
    style M fill:#fffbeb,stroke:#b45309
```

**目的：** 讓「排除某一行」與「定案」成為兩個分開、各自留痕的決定。否則主辦可藉移出未確認的參與行「湊成」全員確認而強制定案。

## 三個由這張圖直接得出的結論

**1. 銀行端不需開放任何 inbound**
平台從不主動連線至銀行。所有互動都由銀行端**發起 outbound HTTPS**，經 Caddy（TLS 1.2+）進入 API。因此不需要在銀行防火牆開孔、不需要固定 IP 白名單接收端，也沒有 webhook 重送與簽章驗證的問題。

**2. 沒有非同步元件，狀態機就是全部的協調機制**
無訊息佇列、無排程器、無背景工作。**每一次狀態轉換都由某一次 API 呼叫同步完成**，成功即已落庫。代價是沒有重試機制；好處是**不存在「訊息卡在佇列」的中間態**——任一時刻資料庫的狀態就是事實。

**3. 每一個寫入都同步留痕**
圖中每一個箭頭在成功後都會同步寫入 `AuditLog`（動作、執行人、所屬行、目標案件、時間、來源 IP）。稽核軌與主流程在**同一個請求內**完成，不是事後補寫，因此不會出現「有動作但沒紀錄」。
